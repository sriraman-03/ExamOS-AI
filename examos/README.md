# ExamOS AI — Your Personal AI Exam Operating System

ExamOS AI turns a student's own syllabus, notes, textbooks and previous-year
papers into an interactive exam preparation system: chat with your material,
generate quizzes, get weak-topic analysis, a personalized study plan, quick
revision sheets and timed mock exams — all backed by a real RAG pipeline over
your own documents.

This is a working MVP, built and scoped around the priority order below
(PDF upload → RAG chat → quiz generation/evaluation → weakness detection →
dashboard/analytics, with planner, revision, exam mode and PYQ analysis as
fully functional but simpler features). See **Scope & simplifications** at
the bottom for exactly what was traded off to ship a working end-to-end
product instead of a partially-built everything.

## How it works — the RAG pipeline

```
Upload PDF → extract text → clean → chunk (900 chars, overlap 150)
    → store chunks in SQLite
    → on a question: TF-IDF vectorize query + your chunks → cosine similarity
    → top-k chunks → sent as context to the LLM (or extractive fallback)
    → answer + source references
```

Retrieval uses a per-request TF-IDF index over the asking student's own
chunks rather than a separate vector-DB service — same pipeline shape
(embed → search → retrieve → generate), zero extra infrastructure to run,
and a one-function swap (`app/rag/retriever.py`) if you want to plug in
Chroma/FAISS + real embeddings later.

## Demo mode (no API key required)

Every AI feature (chat, study explanations, quiz generation, answer
evaluation, weakness recommendations, study planning, revision sheets, PYQ
analysis) has a rule-based / extractive fallback. Leave `ANTHROPIC_API_KEY`
blank in `backend/.env` and the entire app is still fully clickable and
demoable — quizzes generate from your uploaded text, chat answers extract
the most relevant passage, plans are built from a deterministic scheduler,
etc. Add a real key and the same endpoints switch to full LLM generation
automatically — no code changes needed.

## Local setup

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
cp .env.example .env
# Edit .env: optionally add ANTHROPIC_API_KEY, otherwise demo mode is used.
uvicorn app.main:app --reload --port 8000
```

The SQLite database and `data/uploads/` are created automatically on first
run. API docs are auto-generated at `http://localhost:8000/docs`.

### Frontend

```bash
cd frontend
npm install
cp .env.example .env   # VITE_API_BASE defaults to http://localhost:8000
npm run dev
```

Open `http://localhost:5173`. Register a new account — a sample "Computer
Networks" subject with demo topic performance and quiz history is seeded
automatically (Section 25 of the spec), so Analytics/Weakness/Dashboard are
populated even before you upload anything.

Full interactive API documentation (every endpoint, request/response

- ReDoc: `http://localhost:8000/redoc`

Route groups: `/api/auth`, `/api/subjects`, `/api/documents`, `/api/chat`,
`/api/study`, `/api/quiz`, `/api/weakness`, `/api/planner`, `/api/revision`,

## Database

SQLite (`backend/data/examos.db`), created automatically via
`Base.metadata.create_all()` on startup — no migration step needed for the
MVP. Tables: `users, subjects, documents, document_chunks, chat_messages,
quizzes, questions, quiz_attempts, answers, topic_performance, study_plans,
study_tasks` — matching the spec's data model, with every row scoped to a
`user_id` so student data stays isolated.

## Deployment

**Frontend (Vercel):**
1. Push `frontend/` to a repo, import into Vercel.
2. Set the environment variable `VITE_API_BASE` to your deployed backend URL.
3. Build command `npm run build`, output directory `dist`.

**Backend (Render / Railway):**
1. Push `backend/` to a repo, create a new web service pointing at it.
2. Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
3. Set environment variables from `.env.example` — at minimum `JWT_SECRET`
   and `FRONTEND_ORIGIN` (your Vercel URL); add `ANTHROPIC_API_KEY` to leave
   demo mode.
4. SQLite works for a single-instance MVP deploy. For anything with more
   than one backend instance, swap `DATABASE_URL` for a hosted Postgres
   connection string — the SQLAlchemy models don't need to change.

## Security notes

- Passwords are hashed with bcrypt; JWTs are signed with `JWT_SECRET` and
  expire after 7 days.
- API keys and secrets are read from environment variables only — nothing
  is hardcoded, and `.env` is git-ignored.
- Uploads are validated for file type (PDF only) and size (`MAX_UPLOAD_MB`).
- All content endpoints filter by the authenticated user's `id`, so one
  student can never see another's documents, chats, or quiz history.
- Unhandled exceptions return a generic message; no stack traces reach the
  client.

## Scope & simplifications (read before demoing)

Built in the priority order the spec itself lays out (Section 26), so
every feature above the line is fully functional rather than some features
being polished and others fake:

- **Retrieval** uses TF-IDF over the student's own chunks instead of a
  standalone ChromaDB/FAISS service — same pipeline shape, swappable later,
  no extra infra to stand up for a demo.
- **Exam Mode** topics are entered as a single comma-separated string
  (stored as one `topic` field on the quiz) rather than true structured
  multi-subject/topic weighting — question generation and grading are fully
  real, the topic model is just simpler than a multi-topic exam engine.
- **Short-answer grading** in demo mode uses keyword-overlap scoring rather
  than semantic evaluation; with an API key it uses the LLM for real
  evaluation.
- **Adaptive quiz** logic is a straightforward three-tier (easy → medium →
  hard) step based on the last attempt's accuracy, per the spec's own
  guidance not to over-engineer it.
- Every one of these has a clearly labeled "demo mode" badge/note in the UI
  or API response so it's never silently pretending to be something it
  isn't.
